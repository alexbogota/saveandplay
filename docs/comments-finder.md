# Поиск постов для комментариев (Bluesky)

Решение владельца 13 октября 2026: поиск постов делает программа, а не чат. Программа ничего не публикует. Claude в чате только читает короткий список и пишет варианты ответов. Отправляет ответы владелец вручную. Причина: поиск через чат съедал много токенов (страницы поиска целиком), а думать над ответом может только Claude.

## Как это работает
- `npm run comments:find` (программа `scripts/comment-candidates.mjs`, логика `scripts/lib/comments.mjs`). Входит в Bluesky по паролю приложения, ищет по 4 запросам из РАЗНЫХ групп (запросы идут по кругу), отсеивает мусор и пишет `drafts/comments-prices.md` (короткий список, 1–2 тысячи токенов), `drafts/comments-prices.json` и `drafts/comments-state-prices.json` (очередь запросов и свежие посты). Папка `drafts/` не попадает в git.
- Отсеивается само: боты, магазины и студии (по нику и имени), посты разработчиков (wishlist, demo, #indiedev), взрослые метки, не английский, старше `maxAgeHours` (30), закрытые для ответа (у поста есть список разрешённых), посты, на которые аккаунт уже отвечал (программа читает свои ответы), посты с несколькими ссылками.
- Баллы: вопрос +3, тема +2, мало ответов +1, свежий +1, вес группы. Порог `minScore` 5. Посты без слов про игры (книги, комиксы с Humble Bundle) отсеиваются (`requireAnyWord`). Спорные темы (ИИ в играх и т. п.) идут отдельным блоком «Heated», ответ только нейтральный и по фактам.
- Широкий охват (решение владельца 13 октября, временно, пока аккаунт новый): группы `broadPlaying` и `broadAsk` ищут общие игровые разговоры (что дочитали, во что играют, просят рекомендации). Выключить: `enabled: false` в этих двух группах. Правила ответов для них в `docs/comments-saveandplay.md`.
- Все настройки в `data/comments-accounts.json` (ключ блока `prices` как в `data/accounts.json`). Новый аккаунт = новый блок, код не меняется. Группы запросов, стоп-слова и веса правятся там же.
- Память «уже показано»: после того как чат показал владельцу список, он сам записывает ВСЕ показанные ссылки в новый файл `drafts/comments-shown-prices-ГГГГММДД-ЧЧММ.json` (массив ссылок). Программа читает все такие файлы и больше не выдаёт эти посты (причина «already shown» в строке Dropped). Посты, на которые аккаунт уже ответил, программа пропускает сама (читает свои ответы). Первый такой файл `comments-shown-prices-20261013-seed.json` содержит всё, что было показано 13 октября.
- В чате: владелец пишет «комментарии saveandplay». С 14 октября чат берёт код и список с GitHub (ветка `comments`), компьютер и папка проекта не нужны, команды в терминале владелец не пишет. Порядок шагов в `docs/comments-saveandplay.md`.

## Что нужно один раз (ВСЁ СДЕЛАНО владельцем 13–14 октября, напоминать не нужно)
1. Пароль приложения Bluesky: Settings → Privacy and security → App passwords → Add. Название любое. Это НЕ основной пароль, его можно отозвать. В чат не присылать.
2. Строка `BSKY_APP_PASSWORD=...` в файл `.env` в папке проекта (он в `.gitignore`).
3. Запуск по расписанию без рук (Windows, один раз в командной строке; НЕ проверено на компьютере владельца):
   `schtasks /Create /TN "saveandplay-comments" /SC HOURLY /MO 6 /TR "cmd /c cd /d C:\saveandplay && npm run comments:find" /F`
   Раз в 6 часов, пока компьютер включён и вы вошли в систему. Убрать: `schtasks /Delete /TN "saveandplay-comments" /F`.

## Проверка и границы
- `npm run comments:test`: 35 проверок на тестовом сервере (отсев, очередь запросов, список, пароль нигде не печатается и не сохраняется, понятные сообщения об ошибках входа).
- НЕ проверено на живом Bluesky: нужен пароль приложения. Первый живой запуск: `npm run comments:find`; программа пишет простым текстом, что нашла и что не так. Если ответ Bluesky окажется другим, чем в тестах, править `scripts/lib/comments.mjs` (функция `createApi`).
- Эффективность отсева (слишком много или мало постов) смотреть по строке «Dropped in this run» в начале списка и подкручивать слова в настройках.
- Запуск на GitHub Actions сделан, см. следующий раздел.

## Запуск на GitHub (без вашего компьютера)
Решение владельца 13 октября: расписание `schtasks` не подошло, поиск запускает GitHub.
- Workflow «Comment candidates» (файл `.github/workflows/comments.yml`; чат не может писать в `.github`, поэтому готовый файл лежит в `scripts/comments-workflow.yml`, и Claude Code переносит его при `/publish`) сам запускается каждые 6 часов (00:17, 06:17, 12:17, 18:17 UTC) и вручную: GitHub, Actions, «Comment candidates», Run workflow. Около минуты на запуск.
- Он делает то же, что `npm run comments:find`, а результат кладёт на отдельную ветку `comments` (сайт не пересобирается): `comments-prices.md` (список), `comments-prices.json`, `comments-state-prices.json` (память между запусками), `comments-shown-prices-*.json` (посты, которые Claude уже показывал). Тот же список виден внизу страницы запуска (Summary).
- Память между запусками обеспечивает `scripts/comments-branch.sh` (load перед поиском, save после). Проверено на тестовом git: первый запуск, повторный, проигранная гонка при записи, файл «shown», добавленный между запусками, настоящая ошибка (запуск краснеет).
- Пароль приложения Bluesky берётся из секрета `BSKY_APP_PASSWORD`. Положить его туда один раз: `npm run comments:secret` (берёт из `.env`, нигде не показывает; нужен `gh`, а если его нет, скрипт покажет три шага вручную).
- Первый запуск начинает с пустой памяти: посты, показанные 13 октября (файл `seed`), на ветке отсутствуют, поэтому один раз могут повториться. Ваши уже отправленные ответы исключаются сами.
- Чат читает список с GitHub (см. раздел ниже).
- Локальный `npm run comments:find` остаётся рабочим запасным вариантом.

## Чат работает через GitHub (14 октября): команды в терминале не нужны
Решение владельца 14 октября: больше не запускать `npm run comments:find`. Теперь так:
- Автозапуск на GitHub каждые 6 часов (19:17, 01:17, 07:17, 13:17 по Боготе) кладёт свежий список в ветку `comments`.
- Чат (`docs/comments-saveandplay.md`, «Process»): подключает репозиторий (`add_repo`), скачивает код с `main`, `comments-branch.sh load`, `comments-show.mjs --record-new`, показывает посты, `comments-branch.sh save ФАЙЛ` кладёт на ветку новый файл «показано». Папка проекта на компьютере не нужна, подойдёт даже телефон.
- Если списку больше 8 часов (автозапуск опоздал или упал), чат сам запускает поиск: `gh workflow run "Comment candidates"` (проверено 14 октября: из чата запускается и проходит за полминуты). Если права на запуск не окажется, владелец нажимает Run workflow на GitHub.
- Если владельца нет сутки: посты старше 30 часов не попадают в список никогда, а список старше 8 часов чат не использует, поэтому вернувшись он начинает со свежего списка, а не со вчерашних постов.
- Чат и автозапуск пишут в разные файлы: автозапуск пишет список и state, чат только ДОБАВЛЯЕТ новый файл `comments-shown-prices-ГГГГММДД-ЧЧММСС.json` и ничего старого не меняет. Поэтому они не могут затереть друг друга, даже если пишут одновременно (проверено тестом). Все файлы «показано» читаются вместе. Память с компьютера владельца (51 пост) перенесена файлом `comments-shown-prices-20261014-migrated.json`.
- Для работы нужно: GitHub подключён к claude.ai (Settings, Connectors) и приложение Claude установлено на репозиторий `saveandplay` (github.com/apps/claude). Сделано 14 октября.
- Локальный `npm run comments:find` остаётся запасным вариантом, но он читает СВОЮ локальную память `drafts/comments-shown-prices*.json`, а не ветку: списком с компьютера чат больше не пользуется.
- Не сделано: файлы «показано» копятся по одному на каждый заход чата (маленькие). Если их станет несколько сотен, добавить в `save` автоудаление файлов старше 21 дня.

## Ленты (чужие подборки постов по теме)
Идея владельца 13 октября: в лентах по играм сидит нужная аудитория, а наших комментариев там нет. Поиск берёт посты и из лент: список `feeds` в `data/comments-accounts.json`. Все посты из лент проходят те же фильтры, что и из поиска (боты, разработчики, язык, повторы, уже отвеченные).
Подключены четыре ленты (просмотр вечером 13 октября, по 20 постов из каждой, то есть цифры приблизительные):
- `pcGaming` («PC Gaming», phusion.bsky.social, 58 лайков ленты): хэштеги PCGaming, Steam, SteamDeck, SteamOS, Valve; около 12 постов в час, много ботов скидок и новостных сайтов, живых людей мало. Вес 2: главная.
- `gamingLiked` («Gaming», steinmakesgames, 9 лайков): только посты с 3 и больше лайков. Попадают популярные посты с сотнями лайков, спорами про ИИ и десятками ответов, где наш ответ теряется. Фильтры такие посты опускают сами (много ответов снижает балл, споры идут в отдельный блок).
- `videogames` («Videospiele/Videogames», vlaandi, 3 лайка): многоязычная (немецкий, испанский, японский), много консолей и ботов, порядка 240 постов в час.
- `gamingNintendo` («Gaming», seanm4c, 1 лайк): Nintendo и Pokémon, реклама карточек, спам, порядка 240 постов в час.
Для двух последних за один запуск мы видим только последний час-два из шести (300 постов), поэтому и польза у них небольшая. Это пробные ленты: счётчики по каждой ленте и группе копятся в `drafts/comments-state-prices.json` (раздел `sources`: запусков, постов, подошло) и печатаются в конце запуска строкой «Sources so far». Через несколько запусков решаем по цифрам, какие ленты оставить: ненужную выключает `enabled: false`.
- Добавить ленту: новая запись в `feeds` (`name`, `url` как в браузере, `weight`, при необходимости `limit` и `pages`).
- Ответ в чужой ленте в самой ленте не виден: лента показывает исходные посты. Польза в другом: автор и читатели ветки видят наш ответ, а лента даёт свежие посты по теме.

## Консоли, язык, реклама (первый запуск с лентами, 14 октября)
В первом списке с лентами из 12 постов почти все были про Switch, PlayStation, Wii, на португальском и японском, от магазинов и новостных сайтов. Теперь программа отсеивает это сама, ещё до списка:
- **Игры только для консолей** (`console only`): в тексте есть слово из `consoleWords` (Nintendo, Switch 2, PS5, PlayStation, Xbox, Wii, Mario, Zelda, Pokémon и так далее) и нет ни одного слова из `pcWords` (PC, Steam, Steam Deck, GOG, Epic, Windows, Linux). Слова ищутся целиком: «switching» не считается. Если пост про Steam и Switch сразу, он остаётся. Списки лежат в `data/comments-accounts.json`; пустой `consoleWords: []` выключает правило.
- **Не английский текст** (`other language (text)`): программа смотрит на сами слова и буквы (португальский, испанский, немецкий, французский, японский, русский и другие), потому что метка языка у постов часто стоит неверно (в списке были португальские посты с меткой «en»).
- **Реклама** (`promo (link and hashtags)`): ссылка и три и больше хэштегов в одном посте.
- К признакам магазинов и новостных сайтов в `skipAuthorWords` добавлены status, depot, shop, store, ign, kotaku и другие; в `skipWords` добавлены «shop now», «read more:» и похожие.
На прошлом списке (15 постов) новые правила оставляют 3 поста, остальные отсеиваются. Проверено на тексте тех постов, а не на живом поиске.
Главные группы `waitForSale` и `backlog` дали в том запуске 0 постов: запросы со словом steam слишком узкие для окна в 30 часов. Добавлены более широкие запросы. Живую проверку даст следующий запуск: смотрите строку «Sources so far».

### Почему в новом списке остались старые посты (14 октября, вечер)
После новых правил список оказался тем же самым: найденные посты хранятся до 30 часов (в `drafts/comments-state-prices.json`, раздел `pool`) и не проверялись заново, поэтому консольные и португальские посты, принятые старыми правилами, оставались. Теперь при каждом запуске все хранимые посты проверяются по ТЕКУЩИМ правилам; убранные пишутся в строке «Dropped in this run» как `earlier finds: ...`. Так же действует выключенная группа или лента (`enabled: false`): её посты уходят сразу. На сохранённых 168 постах проверка убирает 53 (консоли 34, реклама 7, чужой язык 7, магазины и боты 3, не про игры 1, низкий балл 1).
`queriesPerRun` поднят с 4 до 8: поиск делает программа, токены не тратятся, а группы теперь попадают в список почти каждый запуск.

### Решение 14 октября: `videogames` и `gamingNintendo` выключены
Счётчики после 4 запусков (подошло правилам из просмотренных): pcGaming 63 из 297, gamingLiked 13 из 150, videogames 88 из 889, gamingNintendo 63 из 890. Использованных постов из `videogames` и `gamingNintendo` ни одного: после фильтра консолей остаётся шум (мемы, реклама, клипы без описания, чужие темы), и он вытеснял нормальные посты из списка. Владелец согласился выключить обе ленты (`enabled: false` в `data/comments-accounts.json`, там же пометка). Оставлены `pcGaming` (главная) и `gamingLiked`. Вернуть ленту: убрать `enabled: false`. Посты выключенной ленты, уже лежащие в памяти, уходят при следующем запуске (`earlier finds: source switched off`).

## Картинки, видео, цитаты
Список содержит только текст поста, а картинку чат не видит. Поэтому программа под текстом пишет, что приложено: `[image: описание автора]`, `[image, no description]`, `[video ...]`, `[link card: ...]`, `[quotes @имя: ...]`. Посты только с картинкой и без текста в список не попадают. Если пост без описания и зависит от картинки, чат его пропускает или отвечает только на сам текст. Правила для чата в `docs/comments-saveandplay.md`.

## Отсев при чтении: почему были повторы и как это исправлено
13 октября в 20:21 новый чат показал те же 15 постов, что чат в 17:46 (проверено по файлам: совпали все 15). Причина: программа поиска пропускает уже показанные посты только в момент составления списка, а чат читал готовый список, который со времени 17:39 не менялся, и сам ничего не отсеивал. К тому же свежий список с GitHub лежит только на GitHub, на компьютер он не попадает.
Исправление: шаг `scripts/comments-show.mjs` (`npm run comments:show`). Он берёт список `drafts/comments-prices.json`, выкидывает всё, что уже показывалось (файлы `drafts/comments-shown-prices*.json`) и всё старше 30 часов, печатает возраст списка и не больше 8 новых постов, а с флагом `--record ФАЙЛ` записывает новую общую память показанного (старые записи старше 21 дня забываются). Чат запускает его при каждом «комментарии saveandplay» и после ответа кладёт файл на компьютер в `drafts/comments-shown-prices.json`; поиск читает тот же файл. Если список старше 6 часов, без даты или его нет, шаг не показывает постов совсем и говорит, что список нужно обновить: по старому списку чат ответить не сможет (владелец может разрешить более старый список флагом `--stale 24`).
Без `--record` это просто просмотр: ничего не запоминается.
