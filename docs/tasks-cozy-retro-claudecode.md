## Задание 1. Блоки Cozy и Retro в `data/accounts.json` и отбор игр
Цель: два новых аккаунта получают свои посты в ежедневном брифе, без правок кода под каждую нишу.

Что сделать:
1. Добавить в `data/accounts.json` блок `cozy` (Bluesky `@cozygame.bsky.social`) и блок `retro` (Bluesky `@retrogamedeals.bsky.social`, пока выключен: аккаунт ещё не создан владельцем). Mastodon для Retro добавить тем же способом позже, когда владелец создаст аккаунт.
2. Метки (SubID) для ссылок: `bluesky-cozy`, `bluesky-retro` (для Mastodon будут `mastodon-retro`). Ссылки в постах ведут на наши страницы `/deals/...`, в посте всегда `#ad`.
3. Отбор игр по нише, а не по хитам. Для этого дописать в данные скидок жанры и год выхода (брать из Steam `appdetails`, как уже делает `scripts/steam.mjs`) и поставить в блок правило:
   - Retro: игры старше примерно 2005 года и классика GOG, в первую очередь DRM-free. Порог года выбрать по данным и записать в блок.
   - Cozy: спокойные игры по жанрам Steam (симуляторы, казуальные, инди) без насилия по `content_descriptors`. Если подходящих мало, брать расширенную подборку «спокойные игры» и не писать в постах слово cozy там, где игра не уютная.
4. Правила между аккаунтами: одна и та же игра не идёт в основной, Cozy и Retro в один и тот же день; повтор той же игры у одного аккаунта не чаще, чем уже принято в проекте.
5. Kinguin в новые аккаунты не добавлять (по правилам он разрешён только для `prices-kinguin`).
6. Никаких выдуманных цен и отзывов: только данные из `deals.json`. Если для ниши в этот день нет честной скидки, брифу говорить «нет подходящей», а не добирать любую.
7. После этого запустить `npm run tags:research` и записать, какие теги подставились для каждого аккаунта.

Готово, когда: бриф выдаёт отдельные готовые посты для Cozy и Retro, в каждом `#ad` и ссылка на нашу страницу игры; сборка проходит; в конце есть короткий отчёт: сколько игр попало в каждую нишу сегодня. Посты показываются владельцу до публикации, как всегда.

## Задание 2. Страницы `/retro/` и `/cozy/` и короткие адреса профилей
Цель: у каждой ниши своя страница на сайте, собирающаяся сама по тому же правилу отбора, что и у аккаунта (Задание 1 сделано).

Что сделать:
1. Страницы `/retro/` и `/cozy/` генерируются из блоков ниш в `data/accounts.json`, без отдельного ручного списка игр. Новая ниша в будущем = новый блок, а не новый код.
2. На странице: заголовок и короткое вступление (английский, без выдуманных чисел), список текущих скидок ниши с ценами из данных, ссылка на аккаунт ниши, раскрытие партнёрских ссылок так же, как на остальных страницах.
3. Если игр в нише меньше установленного минимума (предложить число, например 6), страница не показывается в меню и закрывается от поисковиков (`noindex`), пока не наберётся; ничего не заполнять заглушками.
4. Добавить страницы в меню и в карту сайта (когда не `noindex`).
5. Короткие адреса профилей в формате, который уже есть (`public/go/.htaccess`): `/go/bsky-cozy`, `/go/bsky-retro`, `/go/mastodon-retro`. Каждый ведёт 302 на `/cozy/` или `/retro/` с `utm_source=<сеть>&utm_medium=social&utm_campaign=profile`. Пока страница скрыта, адрес ведёт на главную с теми же метками.
6. В статьях короткие адреса `/go/` не используются (это проверяет `scripts/article-tools.mjs`), эту проверку не ломать.

Готово, когда: `npm run build` проходит, страницы открываются локально, `/go/...` отвечают нужным редиректом, в отчёте указано, сколько игр на каждой странице сейчас и показывается ли она.

## Задание 3. Поиск постов для комментариев Cozy и Retro (Bluesky)
СТАТУС: сделано 16 октября (пункты 1-7), отчёт в `docs/comments-finder.md`, раздел «Cozy и Retro». Пункт 8 (Mastodon Retro) ждёт аккаунта. Отличие от текста ниже: поиск идёт под входом основного аккаунта (`loginAs`), отдельные пароли не нужны.
Цель: для новых аккаунтов работает тот же поиск постов, что у основного (`docs/comments-finder.md`), и в чате по фразам «комментарии cozy» и «комментарии retro» приходят готовые варианты ответов. Делать после Задания 1 и когда оба аккаунта созданы и заполнены. Код не переписывать: новый аккаунт = новый блок в `data/comments-accounts.json` (ключ блока как в `data/accounts.json`).

Что сделать:
1. Блоки `cozy` и `retro` в `data/comments-accounts.json`, `language: en`, свои группы запросов (первый набор ниже, уточнить по первым спискам), свои стоп-слова, порог и лимиты как у `prices`, только `queriesPerRun` меньше, пока ниши тихие.
   - Cozy, темы: просят уютные и спокойные игры, Stardew Valley и похожие, фермы и симуляторы жизни, «во что играть вечером», уютные игры на Steam Deck, wholesome.
   - Retro, темы: детские любимые игры, классика PC и DOS, «старые игры, которые держатся», старые игры на GOG и их запуск на современном ПК, ностальгия, любимое ретро.
2. Поиск только читает Bluesky, поэтому лучше без новых паролей: искать под уже настроенным входом основного аккаунта (`BSKY_APP_PASSWORD`), а «на что мы уже отвечали» читать по публичной ленте самого аккаунта ниши. Если без собственного входа никак, нужен отдельный пароль приложения для каждого аккаунта: тогда назвать владельцу самый маленький шаг и ничего не просить прислать в чат.
3. Фильтры основного блока рассчитаны на PC-хиты и не подходят как есть: `consoleWords` и `pcWords` отсекают консольные посты, а в Retro разговор в основном про консоли и ностальгию. Для Retro консоли не отсеивать, но отвечать по правилам основного аккаунта (польза, без рекламы, ссылка только если игра есть у нас). Из `skipAuthorWords` убрать слово `games` и похожие, иначе потеряются обычные люди с такими никами.
4. Память «уже показано» и «уже отвечали» отдельная для каждого блока (`comments-shown-cozy-*.json`, `comments-shown-retro-*.json`), как у `prices` и `mastodon-prices`. Workflow «Comment candidates» и `scripts/comments-branch.sh` обслуживают новые блоки так же, без правок кода под нишу. Файл workflow в `.github` чат писать не может, перенос на `/publish`, как раньше.
5. Одна фраза на всё (решение владельца 16 октября): «комментарии saveandplay» берёт сразу все аккаунты: основной Bluesky, Mastodon, Cozy и Retro, с ОДНИМ `add_repo`, ОДНИМ клоном и ОДНОЙ командой (как уже сделано для двух, раздел «Both accounts in one run» в `docs/comments-saveandplay.md`). Блоки показываются по порядку, у каждого своя память «показано», пустой блок допустим. Фразы «комментарии cozy», «комментарии retro» остаются для запуска одного аккаунта. Следить, чтобы общий прогон не раздувался: лимит постов на блок небольшой (например, 8 для Cozy и Retro).
6. Правила ответов для чата: `docs/comments-cozy.md` и `docs/comments-retro.md` по образцу `docs/comments-saveandplay.md`: фразы «комментарии cozy» и «комментарии retro» (читать только свой файл), ответы на английском, голос ниши (тёплый для Cozy, знающий и без снобизма для Retro), сначала польза и интерес, партнёрских ссылок в комментариях нет, ничего не публикуется без «ок». Для нового аккаунта лимит ответов на старте скромный (предложить число, например 5–10 в день на аккаунт), потом по результатам.
7. Тесты: расширить `npm run comments:test` на новые блоки.
8. Mastodon Retro (после аккаунта `retrogamedeals` на Mastodon): блок `mastodon-retro` по образцу `mastodon-prices` по тегам `#retrogaming` и `#retrogames` (около 170 постов в день на mastodon.social). Cozy в Mastodon пока не нужен (около 5 постов в день).

Готово, когда: `npm run comments:test` зелёный, workflow на GitHub создаёт списки для обоих блоков, а в отчёте указано, сколько постов прошло в каждый список при первом запуске и какие слова пришлось подкрутить. Первый показ владельцу: «комментарии saveandplay» (все аккаунты сразу).
